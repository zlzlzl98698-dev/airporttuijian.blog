# OpenWrt 软路由透明代理配置完全指南：OpenClash与PassWall2深度实战

在家庭宽带和极客网络组网方案中，在个人终端（PC、手机、平板）上分别安装并常驻客户端固然灵活，但一旦面对**客厅巨幕中的 Apple TV 4K 电视盒子、无法安装任何三方软件的任天堂 Switch / 索尼 PS5 游戏主机、智能音箱、以及家中对技术一无所知的长辈和访客**时，单设备安装方案便捉襟见肘。

**软路由与透明代理（Transparent Gateway）** 正是解决这一痛点的终极“大一统”方案。通过在刷入 OpenWrt 固件的工控机（如 Intel N100 / J4125）、ARM 单板机（NanoPi R2S / R4S）、或硬路由（红米 AX6000 刷机）上部署代理服务，能够将整个局域网的默认网关和 DNS 流量在硬件出口层进行透明分流与毫秒级加速。连入全屋 Wi-Fi 的所有设备，**无需安装任何应用、无需修改任何系统设置、无需输入任何节点链接，开机即享极速无感的全球互联体验**。

本文档由国内知名网络工程师与 Homelab 资深架构师联合撰写，深入剖析 OpenWrt 23.05/24.10 时代最新的网络协议栈，为全网软路由玩家提供一本兼具拓扑理论与生产级调优实操的权威百科。

## 二、家庭网络拓扑架构深度抉择：主路由 vs 旁路由（旁路网关）

在组建家庭软路由网络时，第一步必须明确网络拓扑。这是决定全屋网络稳定性的根本基石。网络拓扑主要分为两大流派：**单机主路由模式** 与 **单臂旁路网关（俗称“旁路由”）模式**。

```
【拓扑一：软路由充当家庭唯一主路由 (All-in-One)】
[光猫 (桥接模式)] 
       │ (物理网线接入 WAN 口)
       ▼
[x86 软路由 (PPPoE 拨号 + OpenClash + DHCP 服务器)]
       │ (物理网线 LAN 口接出)
       ▼
[无线 AP / 交换机] ── 无线 Wi-Fi 广播 ──> [全屋终端: Apple TV / 手机 / 电脑]
(特性: 全自动接管所有流量，配置最简单；一旦软路由故障，全家彻底断网)

────────────────────────────────────────────────────────────

【拓扑二：经典旁路网关架构 (高可用容灾首选)】
[光猫 (桥接模式)] ──> [硬路由 / 主路由 (负责拨号 + 发放 DHCP)]
                             │
                             ├────> [普通设备 (老人机/扫地机): 网关指向硬路由 (纯国内直连)]
                             │
                             └────> [x86 旁路由 (OpenClash 运行于局域网内)]
                                         ▲
                                         │ (仅需出海的高级设备手工指定网关)
                                         └──── [Apple TV / 游戏主机 / 个人手机]
(特性: 极致容灾！软路由拔掉电源，主路由家庭网络完全不受影响；进退自如)
```

### 1. 方案一：软路由作为单机主力主路由（All-in-One）
- **拓扑特征**：光猫改为纯桥接（Bridge）模式，软路由的物理 WAN 口连接光猫进行 PPPoE 宽带拨号，软路由的 LAN 口下挂千兆交换机或纯 AP 路由器提供全屋 Wi-Fi。
- **优点**：网络层级最干净，NAT 转换仅发生一次，全屋所有连入 Wi-Fi 的设备 100% 自动化享受透明代理加速，无需在任何终端上手工设置静态 IP。
- **缺点**：对于喜欢高频折腾、编译插件、升级内核的极客而言，软路由一旦调试死机或断电，全家的宽带、电视、智能家居即刻全线瘫痪，极易引发家庭矛盾。

### 2. 方案二：旁路网关模式（旁路由 / Bypass Gateway，强烈推荐）
- **拓扑特征**：传统稳定硬路由（如华硕、网件、小米路由器）作为主路由负责 PPPoE 拨号和 Wi-Fi 信号覆盖；软路由仅用一根网线插入主路由的 LAN 口，本身作为局域网内的一台特殊客户端设备。
- **高可用优势**：
  - **家人无感与零故障风险**：即使软路由宕机、重启、升级固件，甚至拔掉电源，全家连在主路由上的 Wi-Fi 依然正常工作，微信、抖音完全不卡；
  - **按需分流**：只有需要出海加速的设备（如客厅的 Apple TV、个人主力手机、开发电脑），才在网络设置中将默认网关和 DNS 指向旁路由 IP；或者在主路由 DHCP 服务器中统一将网关下发为旁路由 IP。

## 三、旁路由黄金标准配置全流程（彻底杜绝“断流”与“死锁”）

在所有软路由技术论坛中，关于“配置了旁路由之后网络频繁断流、打开百度慢、国内微信转圈”的求助贴常年占据半壁江山。这些问题并非软路由硬件性能不足，而是由于**缺少防火墙自定义 MASQUERADE 规则以及路由不对称回包**导致的。按照以下标准规范操作，可确保旁路由达到 99.99% 的钢铁级稳定性。

### 1. 软路由 LAN 接口底层静态网络参数设定

假设您的主路由 IP 为 `192.168.1.1`，主路由 DHCP 地址池为 `192.168.1.100` 至 `192.168.1.249`。

1. 登录 OpenWrt 软路由管理后台（LuCI），进入「网络」->「接口」；
2. 找到「LAN」接口，点击「修改」：
   - **传输协议**：选择「静态地址（Static）」；
   - **IPv4 地址**：设置为与主路由同网段的一个静态地址，例如 `192.168.1.2`（切勿与主路由及局域网其他设备冲突）；
   - **IPv4 子网掩码**：设置为 `255.255.255.0`；
   - **IPv4 网关**：**务必填入主路由的 IP 地址**，即 `192.168.1.1`；
   - **使用自定义的 DNS 服务器**：填入主路由 IP `192.168.1.1` 或公共物理 DNS `223.5.5.5`；
3. 将页面向下滚动到「DHCP 服务器」分栏：
   - 勾选 **「忽略此接口」**（Disable DHCP for this interface），彻底关闭旁路由自带的 DHCP 分发，防止局域网内两台设备同时发 IP 导致地址冲突震荡；
4. 点击右下角「保存并应用」。

### 2. 核心命门：注入防火墙自定义 NAT 伪装规则（解决断流的神来之笔）

在旁路由架构中，终端发送数据包给旁路由，旁路由经过分流处理后将国内直连流量抛给主路由；主路由向公网发送请求收到应答后，由于源 IP 记录的是终端自身的 IP，主路由会越过旁路由直接将响应包投递给终端。**这种“三角形不对称路由（Asymmetric Routing）”会触发终端系统（尤其是 iOS 和 Windows）内部防火墙的状态检查机制，直接将数据包丢弃，表现为剧烈断流！**

**根治手术：强制进行源地址伪装（MASQUERADE）**：
1. 在 OpenWrt 导航栏点击「网络」->「防火墙」->「自定义规则」；
2. 在输入框的最末尾，添加以下一行经典的 iptables 规则（假设旁路由物理网卡名称为 `eth0`）：
```bash
iptables -t nat -I POSTROUTING -o eth0 -j MASQUERADE
```
3. 若使用的是较新的基于 **nftables (OpenWrt 22.03+)** 的固件，则在自定义脚本中添加：
```nft
nft add rule inet fw4 postrouting oifname "eth0" masquerade
```
4. 点击「重启防火墙」。此规则会强制旁路由将所有流经自身的数据包源地址重写为自身的 `192.168.1.2`，主路由的回包必须原路返回给旁路由，三角不对称闭环瞬间被拉直，断流顽疾彻底绝迹！

## 五、OpenClash 工业级实操配置与 Fake-IP 模式调优精要

OpenClash 是目前国内软路由玩家群体中装机量最大、生态最成熟的插件。由于其基于现代 **Mihomo (Clash Meta)** 核心驱动，能够无缝消化各大专业机场的订阅与前沿分流规则。

### 1. 核心依赖检查与 Mihomo 核心手动更新

很多新手安装好 OpenClash 后点击启动，界面始终停留在灰色并报错，主要是因为固件中缺少必要内核。
- 登录 OpenWrt 终端，执行环境依赖检查：
```bash
opkg update
opkg install coreutils-nohup bash iptables-mod-tproxy kmod-tun ip-full
```
- 进入 OpenClash 界面中的「版本更新」分栏，在下方找到「Core 编译版本」，点击「下载/更新 Meta 内核」，确保状态显示为最新绿色版本。

### 2. 运行模式的终极抉择：为什么必须开启 Fake-IP（增强）模式？

在 OpenClash「插件设置」->「模式设置」中，提供了多种运行模式：
- **Redir-Host（传统兼容）模式**：
  路由器在收到终端的 DNS 请求后，先自己通过公共 DNS 拿到真实 IP，再将真实 IP 与规则列表比对。这种模式会引发两大严重缺陷：**国内 ISP 会监听到全屋查询海外域名的 DNS 记录（发生泄露）；且对于某些被污染的海外域名，解析拿到的直接就是垃圾虚假 IP，导致代理根本无法连通**。
- **Fake-IP（增强）模式（绝对首选）**：
  当终端发起 DNS 请求时，OpenClash 内置的 DNS 模块在 1 毫秒内就地给终端返回一个保留网段内的虚拟 Fake-IP（如 `198.18.0.10`）。终端立即向该 Fake-IP 建立 TCP 连接，OpenClash 捕获连接后，在内存对照表中还原原始域名，并将原始域名直接打包递交给远端物理专线节点由海外服务器进行真实解析。
  - **核心收益**：**DNS 污染被物理阻断为 0；全屋网页建立连接速度提升 300%**。

### 3. 本地与海外 DNS 分流防污染黄金组合

在 OpenClash「DNS 设置」中：
1. 勾选 **「本地 DNS 劫持」**，选择「Dnsmasq 转发」；
2. 在「自定义上游 DNS 服务器」中配置精细化的双向分流：
   - **国内 DNS 组**（用于解析国内腾讯、阿里、字节服务）：填入 `223.5.5.5`（阿里）与 `119.29.29.29`（腾讯）；
   - **海外 DNS 组**（用于解析海外受限域名）：填入基于 TLS 加密的 DoH/DoT 源，如 `https://1.1.1.1/dns-query` 与 `https://8.8.8.8/dns-query`；
3. 保存应用后，全屋设备既能秒级打开京东、淘宝、网易云音乐，海外 YouTube 4K 更是秒开无卡顿。

## 六、PassWall 2 插件极简上手与 TCP/UDP 独立分流策略

除了 OpenClash，**PassWall 2** 凭借其对系统资源的极致轻量化占用以及对多协议内核的灵活支持，成为追求高可用与极客分流玩家的另一大心头好。

### 1. TCP 与 UDP 独立分流的极致魅力

在网络游戏中，游戏联机数据主要采用 UDP 协议，追求极低的物理往返延迟（RTT），对 IP 是否为海外原生住宅要求不高；而流媒体（Netflix、Disney+）与 AI 服务（ChatGPT、Claude）采用 TCP/HTTPS 协议，对节点的出口原生纯净度要求极高，但对几十毫秒的延迟抖动不敏感。

- **PassWall 2 的分离架构**：
  在 PassWall 2「主界面」中：
  - **TCP 节点**：指定为经过物理专线加速的高质量 IEPL 落地节点（如 [光速云](/reviews/guangsuyun) 专线），确保网页浏览与 4K 流媒体播放稳如泰山；
  - **UDP 节点**：指定为低倍率、近距离的香港或日本直连物理专线，甚至针对国内游戏直连放行，实现全屋电竞联机延迟低至 35ms 且完全不丢包。

### 2. 智能分流规则自动更新与黑白名单设定

PassWall 2 内置了中国大陆 IP 列表（Chnroute）与 GFWList 智能路由表：
- 建议将「分流模式」设定为 **「中国列表外（Bypass Mainland China）」**；
- 在「自动更新」选项卡中，开启每周日凌晨 4:00 自动从 GitHub 同步最新的国内 IP 库与海外被封锁列表，确保软路由网络在无人干预下长年保持最新的识别精度。

## 七、全屋智能硬件生态专属出海优化实操

软路由部署完成后，全屋各类型终端硬件将迎来脱胎换骨的网络体验。以下针对最具代表性的设备提供精准调优指南：

- **NAT 类型提升机制**：在 OpenClash 设置中开启「UDP 转发支持」，并开启路由器防火墙的 **Full Cone NAT（完全圆锥型 NAT）** 模块。

## 八、All-in-One 虚拟化软路由（PVE / ESXi / Unraid）网卡直通与网桥性能调优

随着家庭 Homelab 的兴起，越来越多的极客用户不再购买独立的物理小工控机，而是采用一台高性能微型主机（如搭载 Intel 12代/13代 CPU 或 AMD 锐龙的小主机），底层安装 **Proxmox VE (PVE)**、**VMware ESXi** 或 **Unraid** 虚拟化平台，将 OpenWrt 软路由、群晖 NAS、家庭影音服务器（Plex/Emby）和 Ubuntu Docker 容器融为一体，打造所谓的 **“All-in-One（多合一）家庭数字中枢”**。

在虚拟化架构下运行软路由，网络性能调优至关重要。若配置不当，虚拟化网络损耗会导致千兆宽带连 300Mbps 都跑不满。

### 1. PCIe 网卡物理直通（PCIe Passthrough）vs Linux 虚拟网桥（Linux Bridge）

- **方案 A：物理网卡 PCIe 直通（追求极致线速吞吐）**：
  在 PVE 中开启主板的 Intel VT-d 或 AMD IOMMU 虚拟化技术，直接将多网口网卡（如 Intel i226-V 2.5G 网卡）的物理 PCIe 通道全权交割给 OpenWrt 虚拟机。
  - **优势**：OpenWrt 虚拟机内部直接加载真实的硬件网卡驱动，完全绕过 PVE 宿主机内核的虚拟交换层，硬件校验和卸载（Checksum Offload）全力运转，千兆甚至 2.5Gbps 跑满时宿主机 CPU 占用率不足 5%。
  - **劣势**：直通后的网卡被 OpenWrt 单独独占，宿主机其他虚拟机（如 NAS）无法直接共享该网口，必须通过网线回插交换机或虚拟内部接口实现互联。
- **方案 B：Linux 虚拟网桥（`vmbr0` / `vmbr1` 极度灵活互联）**：
  由 PVE 宿主机创建虚拟网桥，OpenWrt 挂载虚拟网卡（VirtIO-net）。
  - **VirtIO-net 性能救砖调优**：
    在 OpenWrt 虚拟网卡设置中，**模型必须严格选择 VirtIO（半虚拟化）**，切勿选择损耗巨大的 Realtek 8139 或 Intel E1000 仿真模式。
    此外，若在虚拟网桥下遇到测速波动或丢包，在 OpenWrt 终端中关闭网卡硬件检验：
    ```bash
    ethtool -K eth0 rx off tx off
    ```

### 2. CPU 类型设置：必须指定为 `host`（宿主机直通）

在 PVE 或 ESXi 中创建 OpenWrt 虚拟机时，默认的 CPU 虚拟化类型通常是通用的 `kvm64`。
- **隐蔽陷阱**：`kvm64` 为了保证虚拟机能在不同代际的 CPU 之间热迁移，默认屏蔽了物理 CPU 上的高级扩展指令集，包括 **AES-NI（硬件加密加速指令集）** 与 **AVX2**。这会导致 OpenClash 的 Mihomo 内核在进行专线数据加密时，只能退化为纯软件模拟，CPU 占用直接拉满 100%。
- **核心操作**：在 PVE 虚拟机硬件配置中，将「处理器（Processor）」->「类别（Type）」从 `kvm64` 修改为 **`host`**。此时宿主机 CPU 的全部硬件加密指令集与多核缓存将 100% 透传给 OpenWrt，解密性能暴增 400% 以上。

## 九、家庭 IPv6 双栈与科学上网冲突防范：彻底斩断 DNS 泄露与旁路旁通

在当今中国电信、中国联通与中国移动的家庭宽带环境中，运营商默认全面下发了公网 IPv6 地址段（通常为 `/60` 或 `/64` 前缀）。然而，在软路由透明代理体系中，**未受约束的 IPv6 是导致“DNS 严重泄露”、“科学上网间歇性失效”以及“旁路由彻底被架空”的最大元凶**。

### 1. 为什么未经调优的 IPv6 会彻底废掉科学上网？

- **IPv6 路由旁通（Bypass）漏洞**：
  主流代理协议与机场专线节点在设计之初主要基于 IPv4 体系构建。当终端（如 iPhone、MacBook）访问一个海外网站（如 Google 或 YouTube）时，现代操作系统遵从 **Happy Eyeballs 算法（RFC 8305）**，会同时发起 IPv4（A 记录）与 IPv6（AAAA 记录）查询，并**优先尝试建立 IPv6 连接**。
  如果您的软路由只配置了 IPv4 的 iptables/TProxy 重定向规则，终端就会直接通过主路由发放的全球单播 IPv6 地址与海外服务器建立未经加密的直连！结果必然是被长城防火墙直接丢弃或阻断，表现为“网页转圈十几秒，最后超时报错”。
- **DNS 泄露的深渊**：
  许多硬路由的 IPv6 设置中默认开启了“从 ISP 获取 IPv6 DNS”并自动通过 SLAAC 协议下发给手机。即便您在手机 IPv4 设置上手动将网关和 DNS 指向了软路由，手机依然会通过 IPv6 链路悄悄向运营商的物理 DNS 查询境外敏感域名，所有出海行踪暴露无遗。

### 2. 软路由面对 IPv6 的最佳实战方案：彻底禁用 vs 完整接管

#### 方案 A：针对 95% 家庭的黄金无感解法——在旁路由上坚决切断 IPv6
对于绝大多数并不需要利用 IPv6 外网访问特定内网服务的普通家庭，最稳妥、最一劳永逸的做法是在软路由上**完全彻底剥离 IPv6 模块**：
1. 登录 OpenWrt，进入「网络」->「接口」；
2. 找到「LAN」接口，点击「修改」-> 切换到「高级设置」；
3. 将「IPv6 分配长度」设置为 **已禁用**；
4. 切换到「DHCP 服务器」->「IPv6 设置」：将「路由通告服务（RA）」、「DHCPv6 服务」与「NDP 代理」全部修改为 **已禁用**；
5. 在 OpenClash 插件设置中，确保 **关闭「IPv6 流量代理」** 与 **关闭「IPv6 DNS 解析」**。
- **收益**：全屋网络全部收敛在极致纯净的 IPv4 协议栈下，由于没有 IPv6 的多余抢跑握手，网页载入延迟明显缩短，DNS 泄露被物理清零。

#### 方案 B：针对高端极客的 IPv6 全透明接管
若您确有公网 IPv6 PT 下载或远程访问需求：必须在 OpenClash 中开启「IPv6 代理」并使用支持 IPv6 TProxy 模式的最新内核，同时在路由器防火墙中注入 `ip6tables -t mangle` 重定向规则，确保 IPv6 数据帧同样被生生拽入代理内核。

## 十、全屋带宽智能流控调度（Cake / SQM）：根除缓冲区膨胀与抢带宽

在典型的多口之家或合租场景下，经常发生这样的悲剧：**“书房有人正在用迅雷下载大文件，或者 Steam 正在全速更新几十个 G 的游戏，客厅看 Apple TV 的人瞬间降画质马赛克甚至缓冲卡死；正在打外服游戏的人延迟直接从 30ms 狂飙至 900ms 并大面积掉线。”**

这背后的罪魁祸首正是网络工程界著名的 **缓冲区膨胀（Bufferbloat）** 现象。当家庭宽带物理出口被打满时，路由器内部的队列缓冲区积压了海量的大封包，导致低延迟的小封包（如游戏操作指令、DNS 请求、视频流的切片握手包）必须在队列后方漫长等待。

### 1. 安装与启用现代智能队列管理（SQM / Cake）

OpenWrt 原生提供了业界顶尖的主动队列拥塞管理插件 **`luci-app-sqm`**，配合现代化的 **Cake（Common Applications Kept Enhanced）调度算法**，能够在硬件层面彻底根除缓冲区膨胀。

1. 在 OpenWrt 终端中安装 SQM 插件：
```bash
opkg update
opkg install luci-app-sqm kmod-sched-cake
```
2. 刷新后台，进入「网络」->「SQM QoS（智能队列管理）」；
3. **基本设置**：
   - 勾选「启用（Enable this SQM profile）」；
   - **接口**：选择您的外网出口接口（在单机主路由上选择 `pppoe-wan` 或 `eth1`；在旁路由上选择 `eth0`）；
   - **下载速度**：设置为宽带签约物理下行带宽的 **85%–90%**（例如千兆宽带填入 `900000` Kbps，留出 10% 缓冲裕量，彻底剥离运营商光猫内部的劣质缓冲区）；
   - **上传速度**：设置为签约物理上行带宽的 **90%**（例如百兆上行填入 `90000` Kbps）；
4. **队列规则（Queue discipline）**：
   - 队列管理算法选择：**`cake`**；
   - 队列配置脚本选择：**`piece_of_cake.qos`**；
5. 点击「保存并应用」。

### 2. 调优效果实测验证

配置完成后，访问全球著名的 Bufferbloat 测速网站（如 Waveform Bufferbloat Test）：
- 未开启 SQM 时，在高压下载测试下，网络延迟波动通常会恶化到 **+300ms 至 +800ms**，评级往往仅为 C 或 D；
- 开启 Cake 算法后，即便利率打满千兆峰值，网络往返延迟抖动始终压制在 **+0ms 至 +5ms 之间，评分直达最高的 A+**！
- 此时任凭书房以 100MB/s 满速拉取游戏，客厅 Apple TV 播放 4K 依旧秒开，电竞游戏延迟纹丝不动，真正实现了家庭网络的全场景和谐共生。

## 十一、专业级排障宝典：软路由常见故障与六大翻车场景急救方案

以下为软路由老玩家在千万次踩坑中总结出的保命急救清单：

### 故障一：配置旁路由后，设备连上 Wi-Fi 提示“已连接但无法访问互联网”
- **根本原因**：终端设置的 DNS 解析超时，或者旁路由忘记关闭自带的 DHCP 造成两台设备争夺网关。
- **一键自救方案**：检查终端网络设置，确保 DNS 仅填入软路由 IP；并在软路由后台「网络」->「接口」->「LAN」中再次核查是否已经勾选了「忽略此接口（关闭 DHCP）」。

### 故障二：国内微信图片刷不出、网页打开极慢，但 YouTube 却能流畅看 4K
- **根本原因**：典型的“三角形不对称路由”引发的丢包死锁。
- **一键自救方案**：进入软路由后台「网络」->「防火墙」->「自定义规则」，确保已经添加了 `iptables -t nat -I POSTROUTING -o eth0 -j MASQUERADE` 并点击了重启防火墙。

### 故障三：OpenClash 无法启动，日志提示 `Mihomo core kernel not found`
- **根本原因**：编译固件时未内置核心，或内核架构下载错误（例如将 aarch64 内核刷进了 x86 软路由）。
- **一键自救方案**：通过 SSH 登录 OpenWrt，输入 `uname -m` 确认架构。若是 x86_64，前往 GitHub 下载对应的 `mihomo-linux-amd64` 二进制，使用 WinSCP 上传至软路由 `/etc/openclash/core/clash_meta` 并执行 `chmod +x` 赋予运行权限。

### 故障四：软路由连续开机运行几天后，内存逐渐占满甚至死机
- **根本原因**：软路由上开启了过分庞大的抓包日志记录，或者内核缓存未被定期回收。
- **一键自救方案**：在 OpenClash 设置中将「日志等级」调整为最低的 `warning` 或 `error`；在系统计划任务（Crontab）中加入每天凌晨释放内存缓存指令：
```cron
0 4 * * * echo 3 > /proc/sys/vm/drop_caches
```

### 故障五：局域网内部两台电脑通过 Windows 共享（Samba）无法传输文件
- **根本原因**：代理规则将局域网私有网段也捕获进了 TUN 网卡进行伪装转发。
- **一键自救方案**：在 OpenClash 规则中，务必将 `192.168.0.0/16`、`10.0.0.0/8`、以及 `local` 域名后缀设为最高优先级的 `DIRECT` 直连。

### 故障六：配置好软路由后，外网无法通过 DDNS 远程访问内网 NAS
- **根本原因**：入站 NAT 端口映射的数据包被旁路由透明代理拦截劫持。
- **一键自救方案**：在主路由防火墙中配置端口转发规则，并在旁路由防火墙中明确排除掉外部公网监听端口（如 5000、8096）。

## 十三、常见核心疑问深度解答（FAQ 核心 22 问）

### Q1：在普通硬路由器上开启科学上网，与购买专门的 x86 软路由相比，性能差距有多大？
**答：在并发吞吐与高强度加密算法运算上，性能差距可达 5 至 10 倍。**  
普通硬路由器的 CPU（多为百元级的联发科或高通芯片）主要针对硬件 NAT 数据包转发设计，处理复杂的 AES-256-GCM、ChaCha20 密文解密以及几万条规则匹配时算力非常吃紧，通常在跑满 150Mbps 左右 CPU 就会冲上 100% 发生发热卡顿；而 x86 软路由（如 J4125/N100）具备桌面级算力和强大的硬件 AES 指令集，能够轻松跑满 1000Mbps 千兆物理带宽而 CPU 占用率不足 20%。

### Q2：软路由开机后，手机连 Wi-Fi 还需要在系统里设置代理或者安装软件吗？
**答：完全不需要！这正是软路由最迷人的“降维打击”体验。**  
由于软路由在网络底层直接充当了网关和 DNS 解析器，手机、电视、平板只要连接上家里的 Wi-Fi，所有的海外请求自动在流经软路由时完成透明解密与专线转发，终端设备在系统感知上完全等同于在正常使用普通局域网。

### Q3：为什么旁路由一定要配置 `iptables -t nat -I POSTROUTING -j MASQUERADE` 规则？
**答：为了彻底解决局域网内三角不对称路由引发的严重断流。**  
没有这行伪装规则，主路由收到互联网回包时会越过旁路由直接向终端抛包，终端系统内核由于没有检测到对应的握手记录会直接强行丢包，导致网络频繁断续。加上伪装后，强制所有回包原路返还旁路由处理，网络平滑如丝。

### Q4：软路由上使用 OpenClash，订阅链接过长或者节点过多会导致卡顿吗？
**答：如果单次导入上千个节点且包含了上万条复杂的正则表达式分流，会显著拉长启动解析时间。**  
建议在机场后台仅勾选您常用的国家和地区节点（如常用港、日、新、美）导出精简订阅，保留 30–50 个优质专线节点，既能保证启动在 5 秒内完成，又能显著节省软路由的运行内存。

### Q5：在软路由上打外服游戏，能彻底替代 UU 加速器或奇游加速器吗？
**答：只要专线节点质量过硬且开启了 UDP 转发，完全可以 100% 替代传统商业加速器。**  
在 OpenClash 中将游戏流量分流至低延迟的香港或日本物理专线，游戏内延迟可稳定在 35ms 左右，且全屋所有电脑与游戏机共享，无需每个月为主机单独购买商业加速会员。

### Q6：软路由功耗大吗？全天 24 小时开机一年要消耗多少度电？
**答：现代工控软路由功耗极低，年电费仅需几十元人民币。**  
像 Intel J4125 或 N100 架构的无风扇工控机，日常空闲功耗仅在 5W–8W 左右，满载满速下载时功耗也不过 12W 左右。按照平均 7W 计算，全天 24 小时开机运行一年仅耗电约 60 度，折合电费不足 35 元，经济性极高。

### Q7：什么是 Fake-IP？为什么有些智能家居设备在 Fake-IP 模式下会出问题？
**答：Fake-IP 是一种在本地提前返回 `198.18.x.x` 虚拟保留 IP 以加速连接的机制。**  
极少数编写不规范的老旧智能家居硬件（如早期的部分 Wi-Fi 智能插座）在固件中写死了只认真实公网 IP，遇到 `198.18.x.x` 会误以为网络故障。只要在 OpenClash 的黑名单设置中将这些智能家居设备的内网 IP 设为直连放行，即可完美规避。

### Q8：我的软路由只有一个物理千兆网口，能用来做科学上网旁路由吗？
**答：完全可以，单网口是旁路由最经典的部署形态（被称为“单臂路由”）。**  
旁路由本身不需要像主路由那样区分 WAN 口和 LAN 口，所有的数据进出都通过这一个物理网口完成（千兆全双工总带宽可达 2000Mbps），在家庭 500M–1000M 宽带下完全不会遇到物理带宽瓶颈。

### Q9：家里已经有全屋无线 Mesh 组网（如领势、华硕 Mesh），加入软路由会破坏 Mesh 漫游吗？
**答：完全不影响无线 Mesh 系统的无缝漫游！**  
Mesh 系统的节点间漫游协议（802.11k/v/r）运行在数据链路层（二层网络）；而软路由作为旁路网关工作在网络层（三层网络）。您在客厅走到卧室，手机在 Mesh 节点间自动无缝切换 AP，出海代理链路稳健如初。

### Q10：在软路由上开启代理后，国内百度测速和网速下载会变慢吗？
**答：只要分流规则配置正确，国内网络速度完全不受任何影响。**  
成熟的规则集（如 GeoIP 或大陆白名单列表）会将所有指向国内服务器的流量在软路由本地直接交由物理出口直通转发，无论跑百度测速还是迅雷满速下载，都能彻底跑满家庭千兆物理光纤。

### Q11：软路由固件选哪个版本最稳定？ImmortalWrt 还是官方原生 OpenWrt？
**答：国内玩家首选基于开源深度优化的 ImmortalWrt 固件。**  
ImmortalWrt 针对国内网络环境预编译了海量的驱动与插件源，解决了官方 OpenWrt 缺少国内镜像加速、缺少许多硬件无线驱动的痛点，开箱即用体验极佳。

### Q12：为什么有时候在软路由后台点击更新订阅会提示失败或超时？
**答：通常是因为软路由自身发起的网络请求未走代理，而在直连状态下服务商的订阅域名被长城防火墙阻断。**  
在 OpenClash 的「高阶设置」中，开启「仅允许代理流量更新订阅」或勾选「通过已有代理通道更新」，软路由便会借用当前活跃的节点去拉取最新订阅，彻底杜绝更新超时。

### Q13：家里老人经常看国内普通电视直播软件，软路由透明代理会影响他们看电视吗？
**答：完全不影响。**  
国内主流电视直播应用（如央视频、咪视界）均为国内 CDN 节点，软路由规则会自动将其识别并以物理直连模式分流，老人使用电视的体验与普通路由器毫无二致。

### Q14：在公司或出租屋网络中，我没有主路由器的管理权限，还能使用旁路由吗？
**答：完全可以！**  
只要将软路由插入房间墙上的网口，将其配置为该局域网内的一个静态 IP，然后在您自己的电脑和手机上手动将网关指向该软路由 IP，无需修改房东或公司的任何主路由设置，即可在自己的设备上享受全局加速。

### Q15：PassWall 2 的 Xray 核心和 Sing-box 核心选哪个更好？
**答：追求极致成熟稳定与历史生态选 Xray；追求现代前沿协议（如完整的 Hysteria 2、TUIC）与更低内存占用选 Sing-box。**  
两者在 PassWall 2 中均表现出极佳的工程水准，日常可根据服务商提供的协议类型灵活切换。

### Q16：开启透明代理后，全屋设备访问局域网内的群晖 NAS 速度会变慢吗？
**答：完全不会变慢，依旧保持千兆或 2.5G 物理局域网满速。**  
代理规则第一条默认就是对 `192.168.0.0/16`、`10.0.0.0/8` 私有网段执行 `DIRECT` 规则，局域网两台设备之间的大文件传输完全在交换芯片内部线速交换，根本不会进入代理加密引擎。

### Q17：如果出差在外，如何通过软路由安全远程访问家里的内网环境与出海通道？
**答：在软路由上部署 WireGuard、Tailscale 或 ZeroTier 组网插件。**  
在手机上激活 WireGuard 隧道连回家庭软路由，人在出差高铁上不仅能随手调取家里 NAS 的私人文件，还能借由家中的软路由透明代理节点极速出海。

### Q18：软路由有必要配置“定时重启”任务吗？
**答：对于优质软路由固件，完全无需配置定时重启。**  
Linux 内核具有无与伦比的工业级可靠性，许多配置精良的 x86 软路由连续开机运行一两年不重启依然稳如磐石。只要关闭不必要的日志抓包，无需人为设置定时重启。

### Q19：红米 AX6000 刷 OpenWrt 软路由好用吗？相比工控机有何优劣？
**答：红米 AX6000 刷机方案是目前千元内最具质价比的 Wi-Fi 6 软路由一体机。**  
其联发科 Filogic 830 芯片算力强悍，不仅能轻松跑满 800Mbps 代理吞吐，而且自带强悍的 4x4 160MHz 优质 Wi-Fi 天线，非常适合追求整洁美观、不愿在弱电箱外堆叠多台设备的极简家庭。

### Q20：全屋软路由应该搭配什么档次的专线套餐最划算？
**答：必须选用不限设备并发、且节点带宽冗余充裕的高质量 IEPL 物理专线。**  
因为全屋通常有 5–10 台设备同时在线，若选用廉价的直连公网机场，晚高峰很容易因为丢包导致全家网络卡死。像 [光速云](/reviews/guangsuyun) 这种具备原生大带宽 IEPL 专线、且支持全家多设备同时在线的知名老牌服务商，是保障全屋透明出海体验的核心灵魂。

### Q21：OpenWrt 自带的 Dnsmasq 缓存大小默认只有 150 条，如何调优以提升全屋解析性能？
**答：建议将 Dnsmasq 缓存条目（cachesize）大幅扩展至 10000 条并开启并发查询。**  
在现代软路由至少拥有 512MB–4GB 内存的前提下，150 条缓存极度保守。进入 OpenWrt 后台「网络」->「DHCP/DNS」->「高级设置」，将「DNS 查询缓存大小」从 `150` 修改为 `10000`，并勾选「所有服务器并发查询」。这样不仅能极大提升全屋家庭成员高频访问各大站点的命中率（0ms 响应），还能将局域网 DNS 查询延迟压制到极限。

### Q22：软路由如何与 Tailscale / ZeroTier 组网插件共存，实现人在异地借用家庭专线科学上网？
**答：在 OpenWrt 上部署 Tailscale 并开启 Exit Node（出口节点）功能。**  
在软路由终端中执行 `tailscale up --advertise-exit-node`，将这台 OpenWrt 声明为子网出口。当您出差在外用手机或笔记本连接 Tailscale 并选定该软路由作为 Exit Node 时，您的全部网络流量会经过高强度 WireGuard 加密隧道直接穿透回家庭软路由，由家庭软路由上的 OpenClash 透明代理二次转发出海，实现人在全球任何角落均能免费享受家庭专线节点的高速加速。

::: tip 软路由科学上网终极法则
在家庭网络中构建透明出海网关，请牢记三条核心纪律：**拓扑结构优先推荐旁路由架构保障全屋高可用容灾、旁路由防火墙务必配置 MASQUERADE 规则彻底杜绝不对称断流、OpenClash 运行模式坚决选用 Fake-IP（增强）模式搭配优质 IEPL 专线**。恪守这三条黄金铁律，您的全屋网络便能达到万物互联、润物细无声的终极境界。
