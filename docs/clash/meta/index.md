### 1. 原版 Clash 的历史功绩与深层痛点
原版 Clash 由开发者 Dreamacro 于 2018 年开源，它首次将“规则分流（Rule-based Proxy）”理念带入了大众视野，结束了早年“全局代理”时代频繁导致微信、国内网银无法访问的痛点。然而，随着时间推移，原版内核逐渐暴露出严重局限：
- **内核生态分裂**：作者将基础功能开源，却将核心的 TUN 驱动、Fake-IP 优化与部分高级规则闭源保留在“Clash Premium”二进制中，导致社区无法协同修复深层 Bug；
- **新协议推进停滞**：对于社区呼声极高的 VLESS、XTLS 以及新型 UDP 协议，原作者迟迟未予以原生合并，导致用户在面对日益升级的 GFW 深度包检测（DPI）时显得力不从心；
- **2023 年底的停更事件**：由于不可抗力因素，原作者彻底清空并归档了 GitHub 仓库，宣告了一个时代的终结。

### 2. MetaCubeX 社区接盘：Clash Meta 到 Mihomo 的蝶变
早在原版项目停更前，一支名为 **MetaCubeX** 的开源先锋极客团队就已经创建了名为 `Clash.Meta` 的分支。他们秉持着“彻底打破闭源枷锁、吸纳全网所有先进协议”的开源理念：
- **全面合并 Premium 闭源特性**：将原本闭源的 TUN 虚拟网卡接管、Fake-IP 智能处理机制以 100% 纯开源代码重新实现，供全球开发者自由审计；
- **重命名为 Mihomo**：为了彻底脱离旧版项目的历史阴影，社区正式将项目品牌升级为独立的 **Mihomo**（源自日语“美穗”，象征纯洁坚韧的新生力量）；
- **Go 语言现代运行时重构**：内核升级至最新的 Go 1.22+ 编译流水线，重写了高并发条件下的 goroutine 协程调度与内存回收算法，在高带宽千兆跑满状态下的 CPU 占用率相比旧版直降 40% 以上。

## 三、次世代出海网络协议支持深度剖析

Mihomo 之所以能成为现代科学上网的不可替代的基石，核心在于其对现代加密通信协议的原生全面掌控：

### 1. VLESS-Reality：借壳上市的终极伪装术
在传统的 TLS 伪装方案（如 Trojan、Vmess-TLS）中，出海用户必须自行购买域名并申请合法 SSL 证书。然而，GFW 的主动探测系统会针对这些新注册、没有真实业务访问量的小众个人域名进行行为特征分析，一旦发现流量模式异常便会迅速列入黑名单。

**VLESS-Reality 带来了颠覆性的范式转移**：
- **借用真实大厂证书（Certificate Borrowing）**：服务端在握手阶段，完全不需要自己持有证书，而是直接“借用”大型跨国企业（例如 `www.apple.com`、`www.microsoft.com`、`gateway.icloud.com`）的真实公网 TLS 证书向审查防火墙出示！
- **消灭主动探测**：当 GFW 的探测爬虫尝试连接节点服务器并发送探针数据包时，服务端通过内嵌的专用验证机制发现该请求不是合法客户端发起的，便会将该连接**毫秒级无损透明转发给真正的苹果或微软官网**！探测器收到的是 100% 正规合法的微软官方网页应答，从而在数学逻辑上彻底无法判定该 IP 是否为代理服务器，达成了近乎完美的抗封锁神隐状态。

### 2. Hysteria 2 (HY2)：高丢包恶劣公网下的暴力吞吐王者
传统的 TCP 协议具有严格的“丢包退避机制”：只要公网链路上出现 5% 的丢包，TCP 的拥塞控制算法（如 Cubic）就会误以为网络发生了严重拥堵，自动将传输速度断崖式腰斩至原本的十分之一。

**Hysteria 2 基于 UDP 协议与革命性的 Brutal 拥塞控制算法打造**：
- **无视丢包暴力发包**：不再遵循传统 TCP 懦弱的退避逻辑，只要物理带宽允许，客户端以恒定速率高频发送数据帧；
- **智能丢包重传（Selective Retransmission）**：利用定制化的 QUIC 状态机，仅对真正丢失的微小片段进行精准补偿重发；
- **实战奇效**：在国际海缆光纤受到严重干扰、晚高峰公网丢包率高达 25% 至 35% 的极端恶劣环境下，普通的 Vmess 或 Trojan 节点早已彻底卡死无法播放 720P 视频，而 Hysteria 2 却能逆势轰出 200Mbps 以上的高速吞吐，秒开 4K 60帧视频！

### 3. TUIC v5：基于原生 IETF QUIC 的极简低延迟新秀
与 Hysteria 2 侧重暴力加速不同，TUIC v5 致力于将 IETF 官方标准的 QUIC 协议性能压榨到极致：
- **0-RTT 极速握手（Zero Round Trip Time）**：利用预共享密钥机制，在建立连接的第一个数据包中便直接夹带应用层请求数据，彻底消除了传统 TCP 漫长繁琐的三次握手往返延迟；
- **完美连接迁移（Connection Migration）**：在手机从家里的 Wi-Fi 断开瞬间切换到 5G 移动蜂窝网络的瞬间，由于底层 UDP 通信基于独特的 Connection ID 识别，您的海外视频通话或 SSH 远程终端不会发生任何断连，实现真正的无缝切换。

### 4. Shadowsocks 2022：老牌协议的涅槃新生
Shadowsocks 2022 是针对原版 Shadowsocks 长期存在的重放攻击漏洞与特征检测进行的大规模重构。引入了固定长度的报头加密、更加严格的时间戳滑动窗口防重放机制，使纯对称加密协议在高速大带宽服务器上重新焕发生机。

### 5. ShadowTLS v3 与 AnyTLS：零证书自建的高阶穿透黑科技
除了 VLESS-Reality 之外，Mihomo 内核在社区驱动下，还率先吸纳了 **ShadowTLS v3** 等极具创新性的伪装协议：
- **与真实境外大站无损双工复用**：ShadowTLS 的精妙之处在于，客户端在发起 TLS 握手时，直接与公网真实的权威境外目标（例如各大国际云厂商镜像站）完成真实的密码学握手；
- **微秒级凭证注入与数据交接**：在握手完毕的微秒瞬间，客户端通过内置的 HMAC 挑战响应机制向代理中间件发送专属暗号，随后在维持已有 TLS 物理信道的前提下，无缝切入真正的加密代理数据流；
- **审查视角下的绝对隐身**：在审查防火墙的 DPI 系统看来，该连接完全是一次由真实根证书签发、与跨国大厂服务器之间建立的 100% 正规 HTTPS 通信，根本不存在任何可供特征提取的异常指纹。

## 四、流量嗅探（Sniffer）与域名还原黑科技

这是 Mihomo 相比传统内核在分流准确度上的最重大杀手锏。

```
                     【传统代理漏判 vs Mihomo 域名嗅探与精准还原】
                                         │
        ┌────────────────────────────────┴────────────────────────────────┐
        ▼                                                                 ▼
【传统无嗅探内核 (旧版 Clash)】                                 【Mihomo 智能嗅探引擎 (Sniffer)】
客户端发起请求：CONNECT 104.244.42.1:443                          客户端发起请求：CONNECT 104.244.42.1:443
内核只看到纯数字 IP，无法知晓背后域名                            内核即时拆解 TLS ClientHello 提取 SNI 扩展
只能无奈匹配低效的 IP-CIDR 或被判定为 DIRECT                     精准还原出真实目标域名：api.twitter.com
导致手机 App（推特/电报/奈飞）频繁直连被墙                        完美命中 DOMAIN 分流规则，精确发往最佳专线！
```

### 1. 移动端与原生应用分流失效的终极根源
在电脑浏览器中，网页请求通常伴随着标准的 DNS 查询，代理客户端能轻松获取目标域名进行规则匹配。但在移动端 App（如 Twitter、Telegram、Netflix、Instagram）中，许多软件为了规避本地 DNS 劫持，内部集成了硬编码的远程 IP 列表，发起连接时直接向物理 IP 发送数据包，完全不走系统的 DNS 查询。
- **旧内核的无奈**：由于无法获知该 IP 背后到底对应什么域名，旧版内核只能根据 IP 归属地猜测；如果服务商没有把这个小众 IP 写入分流规则，该流量就会被错误判定为 `DIRECT` 直连，导致 App 频繁转圈打不开。

### 2. Mihomo Sniffer 的工作原理与嗅探全流程
Mihomo 内置的 Sniffer 模块能够在微秒级内对流经内核的 TCP 连接前置握手数据进行轻量级解构：
1. 当检测到连接端口为 `443` 时，嗅探器自动识别其为 TLS 加密握手；
2. 提取 TLS 握手报文 `ClientHello` 中的 **SNI（Server Name Indication）服务器名称指示字段**；
3. 将提取出的真实域名（例如 `api.twitter.com`）重新注入内核路由上下文；
4. 此时分流引擎便可以重新使用 `DOMAIN-SUFFIX,twitter.com` 强规则进行精准匹配，将其正确引导至专线出站策略组；
5. 同时开启 `override-destination: true`，客户端会将底层的目标连接直接覆写为嗅探出的真实域名，从根本上彻底消除了原生 App 频繁连接超时的顽疾！

## 五、现代规则引擎重构：从低效平铺规则到 Geosite 与 Rule-Providers 数据库

分流规则是客户端的大脑。当用户配置了数千条甚至数万条分流规则时，内核的匹配算法直接决定了整台电脑的网络延迟与 CPU 消耗。

### 1. 传统线性扫描 vs 现代 Trie 字典树算法
- **传统旧规则的性能陷阱**：在早期的配置文件中，用户往往将上万行 `DOMAIN-SUFFIX` 规则硬编码平铺在配置文件中。客户端在处理每一个数据包时，必须从第一行开始逐行向下比对，直到命中目标。当规则数量达到 20,000 条时，单次域名判定的 CPU 循环消耗高达毫秒级，造成高并发下的网络吞吐严重受限。
- **Mihomo 的 Geosite 二进制字典树**：Mihomo 全面拥抱了基于二进制 Dat 或高效数据库编译的 **Geosite** 格式。它将全球数百万个域名预先构建为高效的 **前缀树（Trie Tree）**。在匹配域名时，时间复杂度由线性的 $O(N)$ 直降至对数级的 $O(\log M)$，即使装载 50 万条规则库，域名判定的时延也被牢牢锁定在微秒以内，CPU 占用率近乎为零！

### 2. 外部规则集（Rule-Providers）的模块化解耦
Mihomo 允许将分流规则完全从臃肿的单体配置文件中解耦剥离出来：
- 用户只需在主配置中声明若干个规则集链接（例如专门维护广告拦截的规则库、专门维护流媒体的规则库、专门维护中国大陆域名的规则库）；
- Mihomo 会在后台以增量方式定时静默拉取更新，并在本地持久化保存为缓存文件；
- 哪怕某个规则集源暂时宕机，内核依然无缝使用本地缓存正常运行，彻底告别单体配置文件庞大易损坏的弊端。

### 3. 逻辑组合规则（Logical Rules: AND / OR / NOT）重塑精准分流
Mihomo 引入了对布尔逻辑规则的原生支持，使分流判定的灵活性达到了图灵完备级别：
- **`AND` 逻辑组合**：例如 `AND,((NETWORK,UDP),(DST-PORT,443)),REJECT`，可实现针对特定协议和端口的复合拦截，精准封堵 QUIC 导致的流媒体锁区或测速干扰；
- **`OR` 逻辑组合**：例如将多个相关的进程名或网段合并为单条路由决策：`OR,((PROCESS-NAME,code.exe),(PROCESS-NAME,git.exe)),🚀 开发专线`；
- **`NOT` 逆向逻辑排除**：例如 `NOT,((GEOIP,CN)),🚀 节点选择`，一行代码优雅地实现“除了中国大陆流量之外全走代理”，彻底消除了手写数千行冗长黑白名单规则的维护负担。

## 八、Mihomo 内核系统级排障与优化五步法

当运行基于 Mihomo 内核的客户端遇到突发网络异常时，请按以下专业标准流程排错：

### 第一步：排查 Sniffer 嗅探器冲突与白名单豁免
- **表象**：部分特定国内智能家居 App、苹果推送服务（APNs）或局域网投屏功能断开。
- **根因与排错**：某些专有协议虽然运行在 443 端口，但并非标准的 TLS 格式，强制嗅探会导致握手协议头解析失败直接被重置。在 `sniffer.skip-domain` 清单中加入对应服务的域名白名单（如 `*.apple.com`、`*.mi.com`）即可瞬间排除干扰。

### 第二步：TUN 协议栈性能与兼容性调优（gVisor vs System）
- **表象**：开启 TUN 模式后大文件下载速度受限，或在特定 Windows 版本上提示网卡驱动崩溃。
- **根因与排错**：在客户端设置中将 TUN 模式的网络堆栈（Stack）从 `gVisor` 切换为 `System`（系统原生网络栈）。System 模式能够直接调用 Windows 内核驱动执行 TCP 帧切片重组，彻底释放千兆多线程满速下载潜能。

### 第三步：TCP 并发连接（tcp-concurrent）优化
- **表象**：特定海外网页加载时图片卡住不显示，刷新一次又能出来。
- **根因与排错**：开启 `tcp-concurrent: true`。Mihomo 会在建立连接时针对目标域名并发向多个解析出的物理 IP 发送 TCP SYN 握手探测，并自动采纳最先完成三次握手的最快链路，显著消除海外 CDN 边缘节点抖动带来的随机加载卡顿。

### 第四步：Fake-IP 缓存溢出与 DNS 投毒复位
- **表象**：切换节点后长时间访问旧网站依然提示错误或连不上。
- **根因与排错**：在客户端控制面板中一键执行「刷新 Fake-IP 缓存」，并在本地终端运行 `ipconfig /flushdns`。强行清空本地内存中的虚拟 IP 映射表，迫使内核以新节点的路由策略重新进行映射分配。

### 第五步：内核长效运行内存长效监控与 GC 优化
- **表象**：客户端在轻薄本上开机常驻运行多天后，内存从初始的 60MB 逐渐上涨至 300MB 以上。
- **根因与排错**：这是 Go 语言运行时的延迟垃圾回收策略所致。在系统环境变量中注入 `GOGC=50` 参数，可以促使 Go 运行时更加频繁地执行小型 GC，将长效常驻内存严格压缩锁定在 80MB 以内，极致呵护电池续航。

### Q1：Clash Meta 和 Mihomo 到底是不是同一个东西？它们之间是什么关系？
**答：它们是同一个开源项目的两个不同历史阶段名字！**

### Q2：我正在使用的老版 Clash for Windows（CFW）能直接替换为 Mihomo 内核吗？
**答：可以手动替换核心，但强烈建议直接整体换用 Clash Verge Rev！**  
虽然可以将 CFW 目录下的 `clash-win64.exe` 强行替换为 Mihomo 的二进制包，但由于 CFW 的图形界面早已停止维护，其前端界面完全无法展示 VLESS-Reality、Hysteria 2 等新协议的节点卡片，且容易出现前端 UI 渲染错位。直接换用现代客户端是唯一的明智之举。

### Q3：为什么说 VLESS-Reality 是目前全网防封锁天花板级别的协议？
**答：因为它利用非对称密码学“借用”了苹果、微软等全球最高信任等级网站的真实 HTTPS 证书！**  
它不需要出海用户自行注册域名，彻底切断了针对域名注册者信息的溯源链条；同时面对 GFW 的主动探测请求能够实现无损重定向伪装，使审查方在数学逻辑上无法将其判定为代理服务器。

### Q4：Hysteria 2 协议使用的端口能被运营商 QoS 限速吗？
**答：如果使用默认的高位 UDP 端口，在部分对 UDP 极度敏感的省份可能会受到运营商的 QoS 限制。**  
**破局良方**：将服务端与客户端的端口配置为标准的 `443` 端口，并开启 Hysteria 2 自带的端口跳跃（Port Hopping）功能，让数据包完美伪装成浏览网页时的合法 QUIC/HTTP3 流量，运营商根本不敢随意对 443 端口执行一刀切限速。

### Q5：为什么开启了 Sniffer（流量嗅探）后，有时候访问国内某些银行 App 提示证书被拦截？
**答：因为极个别国内高等级安全银行客户端在移动端实现了严苛的“SSL 证书固定（Certificate Pinning）”！**  
当嗅探器尝试分析其握手报文时，触发了银行 App 本地的安全自毁机制。只需在配置的 `sniffer.skip-domain` 清单中添加该银行的专属域名后缀，彻底跳过嗅探即可完美如初。

### Q7：什么是 Mihomo 的 Unified Delay（统一延迟）特性？
**答：这是 Mihomo 为节点测速引入的一项极具人性化的计算优化。**  
在旧版内核中，测速延迟包含了本地向解析服务器发送 DNS 查询的时间偏差。开启 `unified-delay: true` 后，内核会精准剔除本地网络握手波动，真实准确地反映出节点服务器到目标网站的纯粹端到端网络往返延迟，让节点测速数据极具真实参考价值。

TUIC v5 更注重 0-RTT 的极速握手响应和低功耗，连接稳定性媲美 TCP；Hysteria 2 则是一台暴力冲锋的推土机，适合在跨国公网丢包严重的场景下进行大文件下载和超清影音推流。

**答：全面提供 `linux-armv7` 与 `linux-arm64` 的原生构建，软路由用户可轻松满速拉满千兆转发。**

### Q30：为什么现代工业级专线机场必须全面支持 Mihomo 标准？
**答：因为这是在动荡的网络封锁大环境中，唯一能够满足全平台用户对极致速度、极简操作与绝对安全三位一体诉求的工业级底座！**

### Q31：Mihomo 的 `find-process-mode` 参数有何玄机？
**答：用于控制进程查找的系统权限等级。**  
设置为 `always` 时，无论任何数据包，内核均会强行穿透至操作系统内核查找其所属的进程名称，分流精度最高；对于 CPU 极弱的老机器可设置为 `strict` 节省微量开销。

### Q32：使用 Mihomo 内核进行多节点并发测速时，会不会被机场防火墙判定为恶意攻击？
**答：不会。Mihomo 采用了优雅的并发令牌桶机制，将并发测速频率严格控制在合规网络请求阈值之内。**

### Q33：如何通过 Mihomo 的 External Controller 端口进行无头（Headless）状态下的网络状态监控？
**答：直接访问 `http://127.0.0.1:9097` 并配合开源的 Yacd 或 Meta-Cube-Dashboard 网页控制面板，在任何浏览器中均可实时可视化调阅吞吐流量图谱与活动会话。**

### Q34：Mihomo 对于 Docker 容器网络环境支持如何？

### Q35：为什么出海开发团队最推崇“Mihomo 内核 + 企业双 IEPL 物理专线”的组合？
**答：因为这是一套彻底消除了网络摩擦力的闭环生产力航母！**  
Mihomo 从软件层面消除了协议老化、流量识别与分流误判的阻碍；而企业双专线（如 [光速云](/reviews/guangsuyun)）则从物理硬件光纤层面杜绝了晚高峰丢包与公网阻断。两者深度共生，为您打造坚不可摧的无感出海生产力极速引擎！

### Q36：为什么在开启 Mihomo 的 Sniffer 后，部分网站返回的证书名称与真实访问的域名不一致？
**答：这是因为大型互联网公司（如 Cloudflare、Akamai、Fastly）广泛使用了“通配符泛域名证书（Wildcard SSL）”或多域名 SAN 证书！**  
例如访问特定子域名时，握手报文返回的证书主体可能显示为 `*.cloudflare.com`。Mihomo 的 Sniffer 会优先提取请求层实际发送的精确 SNI，而不会被证书层的主题别名误导，因此完全不影响分流规则的精确命中。

### Q37：在高并发多线程下载场景下，Mihomo 的协程调度机制如何防止系统假死？
**答：基于现代 Go 运行时原生非阻塞 I/O 多路复用（epoll / kqueue）与轻量级 Goroutine 架构！**  
与传统线程模型为每个连接分配数兆内存不同，Mihomo 为每个网络连接创建的协程初始仅消耗几千字节内存。即使同时开启 128 线程大文件并行拉取，内核也能以微秒级在协程间调度切换，CPU 核心负载分布极其均匀，绝不拖垮宿主操作系统。

### Q38：为什么有些用户在使用 Mihomo 时，局域网内的群晖 NAS 远程访问 QuickConnect 频繁掉线？
**答：因为 QuickConnect 通信握手涉及国内中继服务器与海外唤醒隧道的混合调度！**  
**一秒自愈**：在自定义规则集的最顶部，加入以下群晖专属直连规则：
```yaml
- DOMAIN-SUFFIX,synology.com,DIRECT
- DOMAIN-SUFFIX,quickconnect.to,DIRECT
```
确保 NAS 的打洞探测流量 100% 走本地物理宽带直连，即可彻底杜绝掉线。

### Q39：如何在 Linux 嵌入式设备或软路由上交叉编译自己专属定制的最小体积 Mihomo 二进制？
**答：利用 Go 官方支持的交叉编译标志位（CGO_ENABLED=0）并剥离符号表：**  
```bash
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -v -trimpath -ldflags "-s -w -buildid=" -tags with_gvisor
```
配合 `-s -w` 链接器参数，可将编译出来的独立静态单二进制文件体积直接压缩至 20MB 左右，非常适合烧录在存储空间受限的低成本软路由芯片中。

### Q40：为什么说 Mihomo 的 Rule-Provider 相比传统规则能够实现零宕机热增量更新？
**答：因为规则集在内存中采用了原子指针交换（Atomic Pointer Swap）技术！**  
当后台定时器触发规则集更新并从远程拉取新文件后，内核在后台单独编译新的 Trie 树，并在编译成功的微秒瞬间，通过原子操作直接替换全局路由指针。整个过程没有任何连接被掐断，实现了真正的电信级零宕机连续性。

### Q41：在面对深度数据包检测（DPI）针对 TLS 握手指纹（JA3/JA4/ClientHello）的主动识别时，Mihomo 有哪些反制手段？
**答：支持 uTLS 客户端指纹伪装（Client Fingerprint Spoofing）！**  
在节点配置中加入 `client-fingerprint: chrome` 或 `safari`，Mihomo 内核在握手时会严格模拟主流 Chrome 浏览器的 TLS 扩展字段顺序、密码套件组合与 GREASE 填充，使 DPI 审查系统完全无法区分这是代理通信还是正常人使用真实浏览器上网。

### Q42：为什么无论协议如何升级，底层的物理专线链路依然是不可替代的基石？

VLESS-Reality 和 Hysteria 2 解决的是“如何在公网审查严苛的环境下尽量存活”；而企业物理专线（如 [光速云](/reviews/guangsuyun)）解决的是“根本不经过公网 GFW 审查，直接在物理内网中以 0 丢包飞驰”。软件协议与物理专线是“倚天剑”与“屠龙刀”的完美共振，二者合一才是高净值出海生产力的终极答案！

### Q43：在 macOS 上使用 Mihomo 进行大规模并发测速或编译时，提示“Too many open files”怎么解决？
**答：这是 macOS 系统默认对普通进程施加的单进程最大文件描述符限制（默认 256 或 1024）过低所致！**  
**一键提升系统限制**：在 Mac 终端中执行 `ulimit -n 65535`，并将其写入 `~/.zshrc` 用户配置文件中保存。即可彻底解除操作系统的文件句柄封锁，让高并发代理连接跑满硬件极限。

### Q44：在家庭组网中，Mihomo 能否同时充当透明网关与全屋 DNS 广告拦截中心？
**答：原生完美支持！且性能全面超越传统的 AdGuard Home 单独串联方案！**  
Mihomo 内置了功能极其完备的高性能 DNS 引擎。只需在软路由上将局域网 DHCP 的 DNS 地址指向 Mihomo 监听的端口，并在 `rule-providers` 中挂载反广告规则集（如 Anti-AD 或 AdGuard DNS 列表）。内核在解析阶段便会在本地微秒级拦截全部智能电视与手机 App 弹窗广告，一机搞定透明加速与全屋无广告清爽环境。
